1.1Composite & enum types — create, insert, queryL5–8
Seen in: ST24 Q5, Q6 · ST26-1 Q43 · ST26-2 Q5, Q7 · E24 Q29 · E22 Q2 · E20 Q9 / E23 Q2 (ROW / ARRAY insert)
Looks like
"Given these CREATE TYPE / CREATE TABLE statements, which SELECT returns…", "What data type is X?", "Complete the expression to get field Y", "Insert a row"
Template — the shape
CREATE TYPE <type> AS (<field1> <type1>, <field2> <type2>);      -- composite
CREATE TYPE <enum>  AS ENUM ('v1', 'v2', 'v3');                  -- enumerated (ordered, fixed)
CREATE TABLE <tbl> (<col> <type>, <col2> <type2>);
INSERT INTO <tbl> VALUES (ROW(v1, v2), v3);                      -- ROW(...) builds the composite
SELECT (<tbl>.<col>).<field>  FROM <tbl>  WHERE (<tbl>.<col>).<field> > x;
--      ^ parentheses around  table.column  are MANDATORY
Keywords to write
CREATE TYPE … ASAS ENUMROW(…)(table.col).fieldcompositeenumeratedobject-relational
Example 1 — "Which SELECT works?" (ST24 Q5)
Product is a composite (name, category, price); Warehouse(product Product, stock integer); SQL function totalStockValue(Product, integer) returns $1.price * $2. Write the SELECT listing name, category, unit price, stock and total stock value.
Show answer & working
SELECT (Warehouse.product).name     AS product_name,
       (Warehouse.product).category AS category,
       (Warehouse.product).price    AS unit_price,
       stock,
       totalStockValue(Warehouse.product, stock)
FROM   Warehouse;
Why: fields of a composite column need (table.col).field; the whole composite is passed to the function as Warehouse.product (no dot-field).
Example 2 — one-liners (ST26-1 Q43, ST26-2 Q5/Q7, E24 Q29)
(a) CREATE TYPE LapPosition AS (lap INT, sector INT, position INT); CREATE TABLE Driver (driver_name TEXT, latest LapPosition); Get the track position. (b) CREATE TYPE inventoryRecord AS (item_name text, quantity integer); — what type is it? (c) A student says a composite column "violates the relational approach" — respond.
Show answer & working
(a) SELECT (latest).position FROM Driver; (also accepted: (Driver.latest).position).
(b) Composite (not enumerated/text/integer).
(c) The design is object-relational: a user-defined composite type lets structured attributes live inside a relational table while SQL, constraints and transactions remain.
(d) Insert example: INSERT INTO StockOnHand VALUES (ROW('gismo', 42, 1.99), 1000); — enum insert is just the string: INSERT INTO person VALUES ('Cyril','happy');
Traps & mark-losers: Forgetting the parentheses → latest.position is read as "table latest". The enum list is ordered; only listed values are legal. In E24 Q29 the paper wrote CREATE TYPE OwnerType (…) without AS — the real syntax needs AS.

1.3Table inheritance (INHERITS)L5–8

Template — the shape
CREATE TABLE parent (id SERIAL PRIMARY KEY, a TEXT, b INT);
CREATE TABLE child  (extra TEXT) INHERITS (parent);      -- gains parent's columns + its own
SELECT * FROM parent;   -- parent rows AND child rows
SELECT * FROM child;    -- child rows only (with the extra column)

Example — result tracing
CITIES(name, population, area), CAPITALS(state) INHERITS (CITIES). Insert ('Johannesburg',2.5,2500) into CITIES and ('Pretoria',1.5,900,'GP') into CAPITALS. What do the two SELECTs return?
Show answer & working
SELECT * FROM CITIES → both Johannesburg and Pretoria (a capital is a city). SELECT * FROM CAPITALS → only Pretoria, with the extra state column.
Example — True/False
"Triggers are automatically inherited by subtables." / "Inheritance enforces foreign-key constraints across parent and child."
Show answer & working
Both FALSE. A trigger must be created on the child as well (re-using the same trigger function; same trigger name allowed on a different table). Constraints other than primary keys are copied; FK/PK are not enforced across the hierarchy.

Example 1 — derived column from an array (ST26-1 essay b, 7 marks)
AUVEnergy(auv_id, stage_energy NUMERIC[], average_energy NUMERIC): compute average_energy automatically on insert/update.
Show answer & working
CREATE FUNCTION calc_avg_energy() RETURNS TRIGGER AS $$
DECLARE
  val   NUMERIC;
  total NUMERIC := 0;
  n     INTEGER := 0;
BEGIN
  FOREACH val IN ARRAY NEW.stage_energy LOOP
    total := total + val;
    n := n + 1;
  END LOOP;
  NEW.average_energy := total / n;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

Example 2 — multi-table logic + status (ST24 Q25; same shape as ST26-1 Q27 and ST25 Q25)
When an order is inserted, reduce the item's stock by the quantity. If stock afterwards < 5 set order_status = 'LowStockOrder' else 'InStockOrder'; if stock is insufficient, raise an error.
Show answer & working
CREATE FUNCTION update_stock() RETURNS TRIGGER AS $$
DECLARE current_stock INT;
BEGIN
  SELECT stock INTO current_stock FROM inventory WHERE item_id = NEW.item_id;
  IF current_stock >= NEW.quantity THEN
    UPDATE inventory SET stock = stock - NEW.quantity WHERE item_id = NEW.item_id;
    IF current_stock - NEW.quantity < 5 THEN
      NEW.order_status := 'LowStockOrder';
    ELSE
      NEW.order_status := 'InStockOrder';
    END IF;
  ELSE
    RAISE EXCEPTION 'Insufficient stock for item_id %', NEW.item_id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER update_stock_trigger
BEFORE INSERT ON orders
FOR EACH ROW
EXECUTE FUNCTION update_stock();

Example — model answers
(1) Arrays: one advantage + one limitation. (2) Triggers: advantages and disadvantages. (3) PL/pgSQL over SQL function. (4) Third-generation DB manifesto vs the Third Manifesto.
Show answer & working
(1) Adv.: store a repeating group (e.g. quarterly sales) in one column — fewer joins, easy to pass to a function. Limit.: breaks 1NF/atomic values, harder to index/query individual elements, less portable.
(2) Adv.: enforce complex business rules, audit changes, maintain derived data automatically, no application code. Disadv.: hidden logic that is hard to debug/understand, performance overhead, not inherited, can be replaced by simple CHECK/FK.
(3) When you need variables, loops or conditionals — e.g. looping over an array and adding only values > 0 (a single SQL SELECT cannot do that).
(4) Third-generation DB manifesto: OO-permissive — extend relational systems with OO features. The Third Manifesto (Date & Darwen): stay strictly grounded in relational theory even when adding OO features. (Per the notes this pair is "reading for the student".)

6.14Window functions & ranking (moving averages, RANK vs DENSE_RANK)L24

Template — the shape
AVG(SUM(x)) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)     -- moving avg: current + 2 previous rows
SUM(SUM(x)) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)     -- moving sum

inner SUM + GROUP BY makes the monthly totals first; OVER then slides the window over them
